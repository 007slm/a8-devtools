# 顶层架构设计哲学与根本红线 (Architectural Principles)

- **全生命周期思维，彻底摒弃打补丁思维 (Lifecycle Thinking vs. Patchwork Mindset)**：
  任何数据、状态、组件或业务流，必须具备自始至终的完整生命周期闭环视图。严禁“头痛医头、脚痛医脚”式的下游补漏。当下游出现非预期表现时，严禁在下游现场增加补丁、探测或自愈逻辑掩盖问题，必须顺着因果链回溯至生命周期的源头完成根因闭环。

- **职责边界自闭环，严禁不确定性外溢 (Boundary Closure & Zero Ambiguity Leakage)**：
  任何模块或处理阶段必须在其职责边界内完成对物理事实的确权与状态自洽，严禁将本该内部消解的不确定性泄露给下游；下游消费链路只消费确凿事实，严禁越界承担弥补上游职责缺失的补偿性设计（如反向探测、事后猜度、假自愈），坚决杜绝职责错位带来的系统脆弱性。

- **拒绝伪健壮性，严禁过度防御与无原则兜底 (Precision Engineering vs. Defensive Overkill)**：
  系统的真实健壮性源于因果关系的绝对清晰与边界的极其精准，绝非源于到处兜底、探测、重试与轮询。把“过度防御”误当成“健壮性”是架构级严重误区。无原则的兜底只会掩盖因果关系的错位，引入幽灵开销与并发暗礁，最终演变成无法维护的死代码与性能陷阱。

- **领域状态与物理本质绝对对齐 (Physical Truth Parity)**：
  系统状态机必须忠实反映物理世界的客观本质。事实对齐即为正常（如源表 0 行且本地物理表已建好为 0 行，两端即为 100% 对齐的 READY 状态），严禁凭空发明脱离物理事实的伪异常状态（如阻断业务可读的伪异常态）割裂正常业务链路。

- **旧模型彻底退役与全局破坏权强制剥离红线 (Clean Deprecation & Zero Legacy Interference)**：
  当系统引入新模型/新架构并逐步退役旧模型（如手动规则加速退役转为自动镜像加速）时，任何因兼容暂时保留的旧入口（Controller、Service 方法、RPC、脚本等），必须在第一时间彻底剥离其对全局共享底层状态（如 CDC 协调器、存储引擎、全局生命周期）的破坏性特权（如全局清空、强杀进程、抹除实例）。旧入口在过渡期内只允许以只读、无害化、局部兜底或安全受限（Fail-Safe 物理自锁）的形式存在，绝对禁止旧入口在传入空参数、默认参数或异常参数时误杀、误停全局共享核心组件。生命周期自动触发源（如 Spring `ApplicationRunner`、`CommandLineRunner`、`@PostConstruct`、`@Scheduled`、事件监听器等）一旦所属功能被弃用或重构，必须连根拔起彻底删除，绝不允许遗留任何在框架生命周期隐式自启动的“幽灵暗算”代码。

# 编码与工程实施红线 (Engineering & Coding Redlines)

- 禁止兜底：不得用默认值、伪造数据、吞异常、绕过校验或临时补丁掩盖问题，必须修复根因。
- 禁止擅自兼容：除非明确要求，不得增加旧版本兼容、双轨逻辑、适配层或额外依赖。
- 高内聚：模块、类和函数必须职责单一，不得混入无关逻辑。
- 低耦合：模块之间保持最小依赖，不得直接修改其他模块内部状态。
- 单向依赖：严格遵守既定分层，禁止跨层调用、反向依赖和循环依赖。
- 禁止猜测：信息不足时先查代码和文档，仍无法确认则提问，不得自行补全。
- 禁止无关修改：仅修改完成当前任务所必需的内容，不得顺手重构或扩大范围。
- 禁止过度设计：不得无必要地新增接口、抽象层、适配器或实体。
- 禁止迁移逻辑污染：一次性数据修复、历史坏数据修复和迁移不得进入运行时代码；优先使用独立 Shell/SQL 脚本，无法安全迁移时由用户明确决定是否删除无效数据。
- 本地凭证保持简单：除非用户明确提出安全合规要求，不增加本地凭证加密、密钥文件、密钥轮换及兼容迁移代码；对外 API 和日志仍不得泄露密码。
- 简单英文命名：变量、函数和类型使用中国程序员常见、见名知意的简单英文，避免生僻、冗长和概念化单词。
- 优先标准库：JDK 或成熟依赖已提供可靠能力时，不得手写重复的资源关闭、集合、并发或字符串工具。
- 减少实体：能用现有领域对象、标准返回类型或简单值表达时，不得新增 DTO、结果枚举、包装实体。
- 数据类型绝对确定性红线：缓存副本（DuckDB）的物理 Schema 必须以源库数据字典（Data Dictionary）为唯一事实源，严禁在运行时根据 CDC 数据载荷或采样数据反向启发式猜测字段类型。源库中任何数值（INTEGER/BIGINT/DECIMAL/NUMBER/FLOAT）、时间（DATE/TIMESTAMP）等强类型列，在 DuckDB 中必须严格对齐为对应数值与时间类型，绝对禁止退化为 VARCHAR。凡物理数值列在缓存引擎中变成字符列，均按 P0 级严重架构故障阻断，E2E 必须建立物理 Schema 强比对断言。
- 严禁幽灵轮询与事后探测 (Zero Phantom Probing)：严禁在心跳（Heartbeat）、定时监控或批处理消费流水线中增加跨线程、跨数据源的反查探测与防抖补偿。事实必须由显式事件流或上游第一现场驱动，严禁以牺牲系统性能与引入并发竞态为代价进行事后猜度。
- 定向约束：当前架构优化任务不得拆分 `StatementServiceImpl`，仅允许在类内进行完成需求所必需的局部修正。
- **旧代码清缴与全生命周期逆向审计红线 (Mandatory Legacy Code Cleanup & Audit)**：
  进行功能重构、迁移或下线时，必须执行“全生命周期逆向审计与彻底清缴”，严禁“只建新房、不拆旧房”式的增量开发。在判定重构完成前，必须逆向检索并清理所有废弃的接口、自动化启动钩子（Runner/PostConstruct/Listener）、定时任务、废弃配置及中间状态，杜绝双轨逻辑与并发竞态。对于暂时无法物理删除的遗留接口，其底层执行链必须强制切断对全局生命周期的直接调用；任何涉及引擎启停、生命周期迁移的改动，必须在完整的真实容器环境中完成全量冷启动与断点续跑验证，确保 0 幽灵代码、0 残留自杀行为。

# 强制校验红线 (Gatekeeper Rules)

- **后端质量红线**：修改 Java/Proto/配置 后，必须执行 `mvn compile` 或全量服务重启编译，确保后端 100% 编译通过；
- **前端质量红线**：修改 JS/JSX/CSS 后，必须在 `turbo-ui` 目录下执行 `npx oxlint` 检查，确保前端 0 error 极速校验通过（开发阶段 Vite 本身支持热更新，严禁执行耗时漫长的 `npm run build` 打包）；
