# 工作记录标准模板与生命周期规范 (`docs/records/`)

> **适用范围**：由 `a8-agent-mind` 插件统一维护，适用于宿主机全部纳入双层文档治理的仓库。  
> **文件命名**：`docs/records/YYYYMMDD-<TYPE>-<MODULE>-<SUBJECT>.md`  
> **允许类型 (`<TYPE>`)**：`SPEC`（技术规范/设计）、`ADR`（架构决策/取舍）、`BUG`（深层机制故障复盘）。常规小改与简单修 Bug 不写工作记录。

---

## 一、标准头部与正文骨架（写记录直接复制下方区块）

```markdown
# <TYPE>：<一句话明确主题>

- **日期**：YYYY-MM-DD
- **状态**：进行中 | 已落地（当时有效） | 部分失效（被 YYYYMMDD-... 更新） | 已废弃（被 YYYYMMDD-... 取代） | 已暂缓
- **域**：<对应 docs/evergreen/<domain>.md，多个用逗号分隔>
- **取代**：<若本记录推翻了某旧记录，填被取代文件名；否则写 无>

---

## 1. 问题与目标

- **要解决的问题**：当前系统的真实断点、限制或演进触发原因（附物理证据或量化数据）。
- **设计目标**：本次要达成的结果；如适用，简要说明明确不做的范围。

## 2. 核心设计与结论

- 只写生效的契约、边界、状态流转、数据结构、关键取舍（以及否决过的替代方案）。
- 严禁把“先改了 A 文件又发现报错再改 B 文件”的过程流水账写进正文。

## 3. 当时验证范围

- 明确写出**当时**执行并观察到结果的具体命令、用例与环境限制（例如 `cargo test --workspace`、`npm run build`、接口实测路径），不写笼统的“已验证通过”。

## 4. 对常青文档的影响

- 指出本次结论应整合进哪篇 `docs/evergreen/<domain>.md` 的哪一部分，以及是否需要回溯标废既有记录（供 `docs-curator` 核验同步）。
```

---

## 二、状态枚举与旧记录“事后失效”闭环

1. **禁止“当时验证通过”误导后人**：工作记录反映的是写作当时的技术快照；后续一旦出现新方案否定、替换或下线旧方案，**不能保留看似现行有效的状态**，也不能删改旧记录原本的验证正文。
2. **仅允许以下 5 个标准状态前缀**：
   - `进行中`：设计或实现尚未收口。
   - `已落地（当时有效）`：记录中的核心方案当前仍符合系统设计，且当时已落地验证。
   - `部分失效（被 <新记录文件名> 更新）`：核心骨架仍有效，但其中部分契约、边界或实现路径已被后续记录取代。
   - `已废弃（被 <新记录文件名> 取代）`：整套方案已被后续设计否定或下线（DevTools 文档浏览器自动归入「暂缓/已废弃」分页）。
   - `已暂缓`：中途暂停或延后实施。
3. **顶部失效横幅（紧贴 `取代` 与分隔线 `---` 之间插入）**：
   当某份旧记录变成 `已废弃` 或 `部分失效` 时，由 `docs-curator` 在保留其下方历史正文的前提下，在头部插入醒目横幅：

```markdown
> **[已失效 / 已被取代（YYYY-MM-DD）]**
> 以下正文为当时历史快照（当时验证结论仅针对旧方案）。该方案已被 [新方案标题](YYYYMMDD-....md) 取代，当前系统真相请以常青文档 [domain.md](../evergreen/domain.md) 为准。
```

（若为部分失效，标题改为 `> **[部分失效（YYYY-MM-DD）]**` 并写明具体哪一部分被哪份新记录取代。）
