# 工作记录标准模板与生命周期规范 (`docs/records/`)

> **适用范围**：由 `a8-agent-mind` 插件统一维护，用于**事后复检与演进溯源**（非日常主读，写给 `Stop` / `Judge` / 审计追溯看，不堆代码实现流水账）。  
> **文件命名**：`docs/records/YYYYMMDD-<TYPE>-<MODULE>-<SUBJECT>.md`  
> **允许类型 (`<TYPE>`)**：`SPEC`（契约/边界规范）、`ADR`（架构决策与取舍）、`BUG`（深层机制根因复盘）。常规小改与简单修 Bug 不写工作记录。  
> **措辞与术语**：与常青文档共用本仓 `docs/glossary.md`——除通用技术词和反引号真实代码名外，只使用术语表内词汇；不在术语表中的概念，要么补入 `docs/glossary.md` 用普通话定义，要么在正文直接用普通话写清，严禁生造未定义简称或黑话。

---

## 一、标准头部与正文骨架（复检导向，默认每节 2～4 条要点）

```markdown
# <TYPE>：<一句话明确主题>

- **日期**：YYYY-MM-DD
- **状态**：进行中 | 已落地（当时有效） | 部分失效（被 YYYYMMDD-... 更新） | 已废弃（被 YYYYMMDD-... 取代） | 已暂缓
- **域**：<对应 docs/evergreen/<domain>.md，多个用逗号分隔>
- **取代**：<若本记录推翻了某旧记录，填被取代文件名；否则写 无>

---

## 1. 问题与目标

- **约束与现象**：当时什么真实限制、证据或故障触发了本次工作（附关键报错/实测极限，避免长篇日志）。
- **目标与非目标**：本次解决的边界，以及明确不做的范围。

## 2. 核心设计与结论

- **最终决定 / 契约**：生效的核心架构选择、边界或状态守卫（不叙写“先改A再改B”的代码过程）。
- **否决备选与代价**：明确拒掉的替代方案及原因（`ADR` 必写）；`BUG` 写明完整根因链与不变量守护。
- **重审触发条件（`Reconsider when`）**：哪些外部假设或约束变化时应推翻本方案（不适用可省略）。

## 3. 当时验证范围

- **已验证**：当时真实运行的编译、单测、Lint 或实机验证命令与核心结果。
- **未覆盖 / 依赖边界**：明确未测范围或依赖环境限制，防止后续复检误判为“全量包过”。

## 4. 对常青文档的影响

- 指出哪条硬约束应按准入规则合入 `docs/evergreen/<domain>.md`（以及是否需标废旧记录）；若仅作过程留档且常青已覆盖，写明原因。
```

---

## 二、状态枚举与旧记录“事后失效”闭环

1. **禁止“当时验证通过”误导后人**：工作记录反映的是写作当时的技术快照；后续一旦出现新方案否定、替换或下线旧方案，**不能保留看似现行有效的状态**，也不能删改旧记录原本的验证正文。
2. **仅允许以下 5 个标准状态前缀**：
   - `进行中`：设计或实现尚未收口。
   - `已落地（当时有效）`：记录中的核心方案当前仍符合系统设计，且当时已落地验证。
   - `部分失效（被 <新记录文件名> 更新）`：核心骨架仍有效，但其中部分契约、边界或实现路径已被后续记录取代。
   - `已废弃（被 <新记录文件名> 取代）`：整套方案已被后续设计否定或下线（DevTools 文档浏览器自动归入「暂缓/已废弃」分页）。
   - `已暂缓`：中途暂停或延后实施。
3. **顶部失效横幅（紧贴 `取代` 与分隔线 `---` 之间插入）**：
   当某份旧记录变成 `已废弃` 或 `部分失效` 时，由 `docs-curator` 在保留其下方历史正文的前提下，在头部插入醒目横幅：

```markdown
> **[已失效 / 已被取代（YYYY-MM-DD）]**
> 以下正文为当时历史快照（当时验证结论仅针对旧方案）。该方案已被 [新方案标题](YYYYMMDD-....md) 取代，当前系统真相请以常青文档 [domain.md](../evergreen/domain.md) 为准。
```

（若为部分失效，标题改为 `> **[部分失效（YYYY-MM-DD）]**` 并写明具体哪一部分被哪份新记录取代。）
