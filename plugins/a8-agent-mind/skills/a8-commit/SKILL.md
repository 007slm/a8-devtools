# 标准化 Git 提交与强制前置审查闸门 (`a8-commit`)

本技能是代码落库前的**唯一强制质量总闸门**：把日常对话从回合级 `Stop` Hook 打扰中彻底解放出来，并在真正提交 GitHub 前统一执行「风险文件拦截 → 确定性门禁 → Decisions API 概率初筛与 `arch-judge` 语义红线终审 → 文档收口 → 原子拆分与无署名推送」。

---

## 零、触发边界与强制铁律

1. **仅限用户主动触发**：唯有用户显式输入 `/a8-commit` 或明确指示“提交代码 / 提交 GitHub / commit”时才可执行；日常编码、修 Bug 或对话结束时**严禁**自动 `git commit` 或 `git push`。
2. **默认全量强制，仅用户显式传 `fast` 可跳过 Step 3 语义红线审查**：
   - 默认 `/a8-commit` 必须完整走完下文 6 步流水线；一旦确定性门禁失败或语义红线判 `VIOLATED`，**强制阻断本次提交**，必须修完并复检通过后再提交。
   - 仅当用户显式附带 `fast` / `--fast` / 「快速提交」（如 `/a8-commit fast`、`/a8-commit fast nopush`）时，仅跳过 **Step 3 三段式红线语义审查**（`judge_router` / Decisions API / `arch-judge`），省去纯文档、紧急小修或刚审完二次提交的耗时与 Token；**Step 1 敏文件/无关改动拦截、Step 2 仓内确定性编译与 Lint 门禁、Step 4 文档核验、Step 5 无署名提交与 Step 6 水位同步依然强制执行**。**严禁 AI 在用户未显式要求时擅自启用 `fast`**。
3. **纯净直通、有风险必停步**：工作区全部为当前任务干净变更且全部前置检查通过时，**直接按模板完成提交与推送并汇报，无需再问一遍**；但命中以下任一情形必须先停步调用 `ask_question` 确认：
   - 工作区存在敏感/私密或运行态文件（见 Step 1 拦截清单）；
   - 工作区混杂明显属于其他在途任务的无关改动；
   - 跨多仓库提交且范围不明确；
   - 架构审查返回 `REQUIRES_APPROVAL`（需用户显式拍板的设计权衡）。
4. **参数自由组合（默认自动推送）**：
   - 执行 `/a8-commit` 默认完成 `git commit` 后自动 `git push origin <当前分支>`；
   - 附带 `nopush`、`no-push`、`onlycommit`、`only-commit`、「只提交不推送」或「暂不推送」时，只做本地 `git commit`；
   - 附带 `fast`、`--fast` 或「快速提交」时，跳过 Step 3 语义红线审查；可与 `nopush` 任意组合（如 `/a8-commit fast nopush`）。
5. **绝对无 AI 署名 + 历史安全红线**：
   - **严禁署名**：Commit 正文与末尾**绝对不加** `Co-Authored-By:`、`Generated by` 或任何 AI 署名尾巴；
   - **严禁破坏历史与绕过钩子**：严禁 `git push --force`、`git commit --no-verify`，严禁 `--amend` 已推送的远端提交。

## 一、标准 Commit Message 格式规范

### 1. 标题行（必填）

```text
<type>(<scope>): <一句话直白说清核心结果，建议 <= 50 字，末尾不加句号>
```

- 标题直给物理事实与动作结果（如“卸载 Stop Hook 并迁入提交前红线审查闸门”）；
- **严禁 AI 空话**：禁止“优化代码结构”“提升可维护性”“修复若干问题”“完善相关逻辑”；
- 破坏对外契约、协议或配置兼容性时，在 `:` 前加 `!`（如 `feat(grpc)!: 移除旧版非流式查询接口`），并在正文注明 `BREAKING CHANGE:` 与迁移动作。

### 2. `<type>` 类型白名单（严格 7 种）

| Type | 适用场景 | 标题示例 |
| :--- | :--- | :--- |
| `feat` | 新功能、新技能、新能力上线 | `feat(a8-agent-mind): 新增 a8-commit 提交前强制质量闸门` |
| `fix` | 缺陷修复、异常边界根治 | `fix(scan): 按日期方向过滤历史反向取代记录误报` |
| `perf` | 性能、内存、Token 或构建耗时优化 | `perf(cdc): 引入预编译列序计划将冷快照吞吐提升 51.7%` |
| `refactor` | 纯结构重构、删死代码（不改外部行为） | `refactor(a8-agent-mind): 卸载 Stop Hook 并将红线审查迁入提交门禁` |
| `docs` | 文档、常青指南、验证地图、注释清理 | `docs(verify): 补充 D5 提交门禁与夜间扫描实机判据` |
| `test` | 仅增补或修正单测、基准、UI 验收脚本 | `test(agent-mind): 补齐 verify.md 只读拦截单测` |
| `chore` | 依赖升级、构建脚本、Lint 门禁、发布配置 | `chore(release): 更新发布脚本 4 项静态门禁清单` |

- **`<scope>` 命名**：直接使用仓内模块或子目录名（如 `devtools`、`cowfs`、`a8-agent-mind`、`cdc`、`intake`、`ui`、`lints`），跨模块最多 2～3 个逗号分隔。

## 二、两档提交模板（按改动体量自动选档）

### 档位 A：轻量模式（适用 1~2 个文件小修、文案调整、单行配置）

仅写标题 + 可选 1 行精炼原因，不为小改写长文：

```text
fix(scan): 排除旧记录反向填写未来日期导致的取代误报

旧版历史记录曾把“取代它的新记录”填在「取代」栏，补入文件名日期与状态反指过滤后 17 条假告警归零。
```

### 档位 B：完整模式（适用功能开发、跨模块重构、深层修 Bug、性能优化）

正文聚焦 **Why（动机）+ What（按模块摘要）+ Verified（真实证据）+ Impact（影响与文档回链）**，不复述逐行 Diff：

```text
<type>(<scope>): <一句话核心结果，<= 50 字>

背景与动机:
- <触发本次改动的真实痛点、系统约束或根因>

核心改动:
- [<模块/目录>] <关键架构/契约/行为变化 1>
- [<模块/目录>] <关键架构/契约/行为变化 2>

验证实证:
- <实际跑过的编译、单测、Lint、Decisions/arch-judge 或实机命令及结果；未覆盖范围如实标明，严禁编造>

影响与关联:
- 影响范围: <受波及模块或“无破坏性变更”>
- 关联文档: <docs/records/YYYYMMDD-...md 或 docs/evergreen/*.md，无则省略>
- BREAKING CHANGE: <仅破坏兼容时保留，否则省略整行>
```

> **Windows 编码与多行提交纪律**：在 PowerShell 提交多行消息时，优先将 UTF-8 无 BOM 文本写入系统临时文件并执行 `git commit -F <tmp>`（提交完毕立即删除临时文件），避免引号与换行转义破坏中文排版。

## 三、6 步强制执行流水线（按序执行，严禁跳过）

### Step 1：全量盘点与敏感/无关文件硬拦截
1. 前置 `[Console]::OutputEncoding = [System.Text.Encoding]::UTF8;`，执行：
   ```powershell
   git status --short -uall
   git diff --stat
   git branch -vv
   git remote -v
   ```
2. **高危文件强制拦截清单**（命中任一项或混杂无关在途改动，立即停步用 `ask_question` 确认范围，绝不顺手暂存）：
   - 授权/密钥/凭证：`*.key`、`license.key`、`.env`、`.env.*`、`*secret*`、`*.pem`、`*.p12`、`credentials*`、含私钥或 API Key 的 `config.json`；
   - 运行产物与临时文件：`logs/`、`*.log`、`tmp/`、`dist/` 临时构建产物或意外落盘的调试脚本；
   - 明显与当前工作主题无关的在途修改。

### Step 2：仓内确定性门禁核验
- 核对目标仓库 `AGENTS.md` / `docs/verify.md` 规定的编译、基础单测与 `scripts/lints/` 机械检查；若最后一次改码后尚未跑通，**必须先补跑全部基础门禁至退出码 `0`**，否则阻断提交。

### Step 3：提交前强制三段式红线审查（Decisions API → 按需语义终审；`fast` 模式跳过本步）
> **快速通道说明**：仅当用户显式传入 `fast` / `--fast` / 「快速提交」时跳过本步 3 段语义审查，直接进入 Step 4，并在 Step 6 汇总表如实标明 `fast 模式（已按用户指定跳过 Step 3 语义红线审查）`；默认 `/a8-commit` 严禁跳过本步。

对本次拟提交的文件集合，按以下三段漏斗检查：

1. **第 1 段 · 元特征与文档路由（`< 50ms`，0 Token）**：
   ```powershell
   py -3 C:/Users/007sl/.gemini/config/plugins/a8-agent-mind/skills/a8-judge/scripts/judge_router.py <目标仓> [--paths <待提交文件...>]
   ```
   - 若本次仅为纯文档/纯文案/局部微调且 `activated_categories` 为空、未触及任何高危架构面，记录“元特征路由未激活架构红线维度”直接绿灯进入 Step 4。
2. **第 2 段 · Decisions API 语义概率初筛（命中即必跑）**：
   - 只要 `activated_categories` 非空，立即运行：
     ```powershell
     py -3 C:/Users/007sl/.gemini/config/plugins/a8-agent-mind/skills/a8-judge/scripts/decisions_client.py <目标仓> <activated_categories逗号拼接> [--paths <待提交文件...>]
     ```
   - 该脚本自动注入 `relevant_docs` 常青设计上下文并调用 `gemini-decision-1` 对 Diff 全量分片裁决。
3. **第 3 段 · `arch-judge` 全仓语义深审（告警或高危面必跑）**：
   - 满足以下任一条件时，**必须**派发隔离上下文子代理 `invoke_subagent(TypeName="arch-judge", Role="Architecture Judge", Workspace="inherit", ...)` 结合 `AGENTS.md`、`relevant_docs` 与完整源码调用链作最终裁决：
     - 第 2 段 `decisions_client.py` 返回 `verdict` 为 `VIOLATED` / `REQUIRES_APPROVAL`，或 `status` 异常（Fail-Closed）；
     - 本次改动触及**跨模块/跨端架构边界或核心依赖增删、公开/持久化契约变更、并发锁/异步状态机重构、或兼容层/旧模型清理**。
4. **裁决执行动作**：
   - `PASSED`：进入 Step 4；
   - `REQUIRES_APPROVAL`：停步用 `ask_question` 向用户展示权衡与依据，获批后方可继续；
   - `VIOLATED`：**强制阻断提交**，清晰列出违规文件、物理因果链与改法，待修复并重跑全套检查转绿后再提交。

### Step 4：文档收口核验（随代码一并提交）
- **严格区分「常青更新」与「工作记录留档」**：更新了 `docs/evergreen/` **绝不等于**免写 `docs/records/`。
- 逐项核对本次拟提交的真实 Diff 是否命中以下任一留档触发条件：① 架构、生命周期或并发模型变更；② 跨模块边界、外部契约或持久化 Schema 变更；③ 状态机、核心不变量或验证入口调整；④ 深层 Bug 根因或显著性能优化；⑤ 单次涉及 **≥ 5 个生产源码文件**的非机械改名改动：
  - **全部不命中（常规小改、纯文案或单点小修）**：免建工作记录，直接进入 Step 5（Step 6 简报注明免建理由）；
  - **命中任一项且本次拟提交文件集合中未新增 `docs/records/YYYYMMDD-*.md`**：**必须**先在当前上下文按 `templates/work-record.md` 补写精炼工作记录（4 项头 + 4 段要点），并顺手轻更对应 `docs/evergreen/`、`docs/verify.md`、`AGENTS.md`（单文件 `< 20,000 B`，**严禁**为此额外启动 `docs-sync` 子代理），复跑文档格式校验后随代码一并提交。

### Step 5：按职责原子拆分 + 标准化 Commit / Push
- 当本次改动包含多个独立职责主题（如「治理与文档」vs「核心业务/性能」，或 TDD「回归测试」vs「修复实现」）时，按显式文件路径 `git add -- <files>` 拆为独立原子 Commit；
- 按档位 A / 档位 B 模板生成无 AI 腔、无署名的 Commit Message 并执行 `git commit -F <tmp>`（随手删 `<tmp>`）；
- 若未指定 `nopush` / `onlycommit` 且存在追踪远端，立即执行 `git push origin <当前分支>`；遇远端 non-fast-forward 立即停步汇报，绝不强推。

### Step 6：收尾回显与文档扫描水位同步
- 若目标仓在 `a8-agent-mind/repos.md` 在管文档仓且本次提交已完成文档对齐，顺手执行：
  ```powershell
  node C:/Users/007sl/.gemini/config/plugins/a8-agent-mind/scripts/scan_docs_sync.mjs --mark-done <repoCode>
  ```
- 输出精炼汇总表，列清：**仓库、分支与推送状态（含远端 SHA 区间）、前置红线审查结论（`fast` 模式须如实注明跳过 Step 3）、提交短 SHA 与标题、文件数、工作区余留未提交文件**。
