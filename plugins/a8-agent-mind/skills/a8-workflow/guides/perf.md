# 指南 3：性能排障与多轮指标调优 (`perf`)

> **适用场景**：解决明确的性能慢点与退化（单次性能排障），或把某个可测指标持续压低到目标阈值（多轮指标调优）。
> **不可逾越红线**：**没有可信的实测基线严禁动手优化；严禁靠读源码猜测哪里是瓶颈。** 跑数前先查阅目标仓库 `<repo>/docs/verify.md` 中的性能基准规范。

---

## 一、 轨道 1：单次性能排障（解决明确慢点或回归）

适用于定位某个慢接口、高内存占用、启动延迟或帧率卡顿并修到达标为止：

1. **纯净基线 + 独立剖析分离**：
   - 先在纯净生产配置下按 `<repo>/docs/verify.md`（或最小实测脚本）跑出改动前基准数字，并过完第 3 节「性能基准防伪 7 问」确认基线可信；
   - 另跑一轮独立剖析（CPU 采样、内存分配 `AllocMB`、GC、I/O 等待或锁竞争）锁定真实限速器并映射回源码 `file:line`。**因剖析器自带开销，严禁把剖析轮跑出的数字当成正式基线或对比成绩。**
2. **按从廉价到昂贵的 7 条优化阶梯逐级排查（前级达标即止）**：
   1. **别做无用功**：彻底停掉结果根本没人消费的计算、日志拼装或冗余查询；
   2. **只做一次**：合并或复用同一生命周期内重复执行的初始化、解析或元数据查询；
   3. **少做点**：缩窄扫描窗口、裁剪传输列、减少无谓深拷贝或批次数；
   4. **延后做**：把启动路径或用户首屏不急需的重工作拆出关键路径，按需延迟触发；
   5. **闲时做**：将可异步处理的审计、刷盘、清理或统计移到后台队列，不阻塞主链路；
   6. **并发做**：对彼此独立的分片改并发执行（先物理拆分共享目标再谈锁）；
   7. **换便宜实现**：前 6 招仍达不到目标时，再改造算法复杂度、存储结构、批写入协议或编解码方式。
3. **小步实施与同面复测**：跨模块边界改形先对齐签名与所有权；每做完 1 个独立改动，立即在同配置纯净环境下复跑基准与剖析（对照改前/改后产物），确保功能零破坏且提升幅度大于轮间波动，再走 [SKILL.md](../SKILL.md) §4 收口。

---

## 二、 轨道 2：多轮指标调优

适用于目标明确且需多轮迭代试错压榨的指标优化（例如“把某导入耗时压降 50% 以上”）：

1. **锚定真实负载与双停步谓词**：
   - 先摸清受影响子系统的结构与真实负载变量（数据规模、历史跨度、状态复杂度、并发路数），选定能稳定复现业务慢点的真实测试负载（复现不出先改负载，不盲目调优）；
   - 确定单一主指标与改善方向，并同时写死**双停步谓词**——`目标阈值` + `最低尝试轮数下限`（例如“中位数耗时比基线降低 >= 50%，且至少完成 10 轮试验”），防止前期撞大运碰到噪声赢一次就提前结束；指标取用户约定值或团队共同商定值，**运行途中绝不允许偷偷放宽标准**。
2. **打造并冻结测试桩**：
   - 写成一条可重复执行的命令，除主指标外，**强制同时输出错误次数（断言 `errors == 0`）与实际完成工作量计数**；
   - 用轻/重两档差异明显的真实负载实测灵敏度（确认重负载真慢、轻负载明显快，且每轮多跑几遍取中位数能盖住波动噪声）；
   - 通过第 3 节「性能基准防伪 7 问」核验后**正式冻结测试桩——后续多轮调优全过程严禁修改测试桩或降低校验难度**；先记录改动前基线分与全套回归门禁全绿状态。
3. **启用实验账本 `logs/<task>-perf.tsv`（不入库）**：
   - 存放于 `.gitignore` 覆盖的 `logs/` 目录，每行记录一轮完整实验（Tab 分隔）：
     `id | hypothesis | change | before | after | delta | tests | verdict(kept/reverted) | note`；
   - 若目标仓库已建有统一历史账本（如 `a8-turbo` 的 `logs/test-history.jsonl` 与 `CdcPipelineBenchmarkIT.java`），同步把关键轮次结果记入统一账本。
4. **单变量逐轮实验循环**：
   - 每轮动手前先看 `logs/<task>-perf.tsv`；每轮只提出 1 个绑定具体代码机制的明确假设（可参考轨道 1 的 7 阶梯由廉到贵排序，但不能因早有微弱改善而绕开双停步谓词）；
   - 仅做这一步最小改码（多个相互独立假设需并行验证时，必须分派至独立 `git worktree` / `CowFS` / `swarm(share)` 隔离运行，主会话审核 Diff）→ 跑冻结测试桩与全套功能回归门禁；
   - **保留判据**：仅当功能回归 100% 全绿、错误数为 0 且主指标改善明确跨过噪声波动区间时才保留并单独记一个清理提交（只 `git add` 改动文件）；其余（含无显著差异、效果存疑或报错）**整步彻底回退**；不管保留还是回退都要在 TSV 账本留一行记录。
5. **突破平台期与正确性红线**：
   - 连续几轮被拒陷入平台期时，切换优化大类（从微调改向批处理、数据布局或减法删冗余）、组合接近过线的思路、或重做一次现场剖析再继续；
   - **正确性与代码简洁度永远优先于指标数字**：破坏功能哪怕提速十倍也必须回退；简化代码且速度不倒退必须保留；达到双停步谓词或剩余方向性价比明显不划算时收口交卷。

## 三、 强制通关门禁：性能基准防伪 7 问与无效判定

在运行基准前，先写一句期待证明的声明（如“60 万行导出 p50 耗时下降 30%”）以及能推翻它的最低门槛与噪声底线；检查本机 CPU 负载与后台干扰（无法清掉干扰时必须 A/B 交替跑来对冲）。

汇报任何耗时、吞吐或资源对比数字前，必须拿着实跑证据回答下面 7 问（注：用户只要粗略摸底时可单跑 1 遍并标明“单次摸底”，但仍必查第 4、7 问；只要涉及技术选型对比就绝不能单跑 1 次）：

| 编号 | 核查问题 | 实证方法与反作弊要求 |
| :---: | :--- | :--- |
| **1** | **为什么没快一倍？（瓶颈限速器在哪）** | 用独立剖析轮抓到的 CPU / 分配 / I/O 等待 / 锁热区或 `file:line` 说明边界；同时检查压测发端是否先打满；不能靠读源码猜。 |
| **2** | **两边都按生产配置充分调优了吗？** | Release 编译、生产 JVM/引擎参数、批大小、连接池、索引与预热/冷热起点必须对齐；单边跑默认未调优参数等于在比配置而非比实现，必先调齐重测。 |
| **3** | **有没有突破物理或算术上限？** | 用磁盘带宽、网络速率、CPU 核数与被改段落原本耗时占比验算（删掉一个原本只占 10% 耗时的步骤，总耗时最多降约 11%，超限说明一定测漏了工作）。 |
| **4** | **错题数是不是 0？产出对不对？** | 拒收、超时或异常早退往往极快；脚本必须统计并断言 `errors == 0`，且核对落盘行数/内容实质正确。 |
| **5** | **可稳定复现吗？（5+ 次 A/B 交替）** | 按 `A, B, A, B...` 交替跑至少 5 轮，报告**中位数与最小～最大波动区间**；差值小于轮间波动即判为“无显著可测差异”。 |
| **6** | **在真实端到端全链路占多大比重？** | 微基准旁并列真实端到端数据规模下的成绩及该局部占比（仅占全链路 1% 的函数提速再多，整体最多快 1%）。 |
| **7** | **工作到底有没有在计时区里发生？** | 核实请求真的打进服务端、结果确实落盘或被消费者完整读完；严防惰性流未拉取、未等待异步结束、编译器死代码消除或静默命中旧缓存。 |

> **强制 `INCONCLUSIVE` 判据**：只要出现以下任一情形——① 声称有提升/回归却指不出限制器；② 对比中存在未按生产调优的一侧；③ 未能核查第 4 问或第 7 问——本次基准**必须判为 `INCONCLUSIVE（无有效结论）`并明列缺口**，严禁当成通过证据交付。

## 四、 性能交卷要点

主回复（遵循 `SKILL.md` §4 不超 40 行）仅呈现核心数字与决定：**指标与单位、基线 → 优化后（中位数 + 区间）、样本轮次、百分比变化、限制器（含 `file:line`）、关键思路及 `logs/<task>-perf.tsv`（或剖面档）路径**；若为持续调优未完全达标但性价比见顶，补充一条“如果继续往下挖最值得试的一步”。
