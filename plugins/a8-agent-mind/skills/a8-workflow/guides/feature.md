# 指南 4：新功能交付、结构重构、原型试错与视觉对齐 (`feature`)

> **适用场景**：新功能开发与跨边界重构、只改内部结构的纯重构、隔离区丢弃式原型试错、像素级 UI 对齐迁移，以及强并发/状态机的形式化或不变量校验。
> **核心铁律**：**先定数据形状与不变量，再写业务逻辑；跨边界改动先比选架构，收口先过注释清理与真实运行验证。**

---

## 一、 模式 1：新功能与跨边界改造

1. **影响面摸底与从零重搭追问**：
   - 先顺调用链查清受影响的上下游模块、存储结构与跨端协议；接入新需求时不硬打补丁，先自问“如果第一天就有这个需求，这套数据结构和接口会怎么从零设计”。
   - 跨模块或公开签名边界改动前：至少构思 **2 套** 类型/签名/所有权方案，择取“每块状态只有一个主人、每种任务只有一条实现路径、调用方需知最少”的那一版（对齐 [mind-rules.md](../../../rules/mind-rules.md) 单向分层与边界唯一校验；无框架依赖的纯逻辑抽成纯函数，方便外壳薄调用）。若同一处局部补丁反复出现，立刻停下重设计。
2. **高分叉无先例决策的多方案比选**：
   - 遇无先例的高风险设计分叉时，先写 **3～6 条可评分判据**；派 2～3 个隔离子代理（各自使用 `swarm` 的 `workspace:"share"` / `git worktree` / `CowFS` 独立目录）仅看任务目标与共有约束，独立产出方案、权衡说明及放弃路线 → 派 1 个只读审阅者按判据打分推荐底座 → 主会话通读全部候选方案选定底座，并**按第一性原理手工融合落选方案亮点（严禁机械拼贴）**；若方案高度收敛直接沿用，若严重分歧则说明判据写糊了，重立问题再跑。
3. **并发与分工四问（写入会话待办，单文件无并发标 `n/a: <原因>` 不删项）**：
   - **前置阻塞门禁**：哪些共有脚手架、基础原语或基线测试桩必须在并行之前先落地？
   - **可独立并行任务**：哪些不相交的文件、服务或层级可以拆出并发执行？
   - **共享可变状态先拆分**：多个写入者同时改同一文件、分支或同一 JSON 对象的不同字段仍存在竞争，先按目标物理隔离，只有确属唯一不变量才加锁或串行；
   - **最小安全拆解单元**：如果由 1 人从头做完最稳妥，直接写明原因。
4. **先定数据形状、强类型边界与幂等收口**：
   - 写逻辑前先敲定核心数据结构与显式状态机，让非法状态在编译或边界解析期直接构造不出来：
     - 用枚举或判别联合替代散落的多个可选字段袋，并做穷尽分支检查（如 TypeScript `never`、Rust `match`、Java 密封枚举/`switch`）；
     - 同一基础类型承载不同业务语义时（如 `RepoId` 与目录路径），用专门包装类型隔离并在构造边界一次性校验；
     - 外部输入（JSON、RPC、CLI、DB 行）仅在系统入口校验解析成内部定型类型，内部直接信任类型不层层防御判空；有权威 Schema 时直接从中派生类型不手写副本；跨文件重复 `if/else` 分支改用查找表或注册表；
     - 状态步骤按“当前物理状态与目标状态”差量收敛以保幂等，锁文件或临时半写入产物带可识别陈旧凭证并用临时文件加原子重命名替换。
5. **高危状态机与并发的形式化 / 随机不变量校验**：
   - 涉及并发竞争、断点重试、水印追赶或复杂协议，单靠手写单测覆盖不到交叉时序时，选用当前仓库成本最低且能落地的验证手段：已有 Quint `.qnt` 模型（如 `a8-turbo` `docs/records/20261118-SPEC-缓存与同步-CDC水位线一致性状态机模型.qnt`）或 TLA+，或者对真实代码跑随机操作序列不变量单测；
   - **紧贴源码与双铁律**：模型中每一步原子动作严格对应代码里不可分割的一步，使用仓内真实符号名，在模型或说明里登记覆盖源码清单与最后核对的 `sync_commit`；
   - **破坏抓虫验证**：写好或改好验证后，必须在本地临时删掉一处校验或对调两步顺序，确认工具真的报错抓出反例后再恢复源码；绝不为了绿灯放宽不变量性质；
   - **状态机可读图与代码重放**：用业务人话而非变量名画状态转移图并标出违背不变量的最短反例路径，**必须按该最短路径在真实代码上写测试或脚本重放证实**（代码跑不出来先疑模型有误）；
   - **模型漂移维护**：源码绕过模型直接改动后，从 `sync_commit` 起 diff 覆盖文件与新增写状态入口，先据源码修改模型（严禁看运行结果凑绿灯），明确区分「模型漂移」与「产品真缺陷」。
6. **逐单元实现与同波次迁移**：按“基础底座与验证桩 → 具体分支 → 全部调用方同波次迁移并立即删掉旧入口”的顺序，每做完 1 个可验证单元立刻跑对应校验转绿，再进下一单元。

## 二、 模式 2：纯结构重构（只改结构，严禁变更行为）

- **严禁夹带功能或修 Bug**：重构途中发现缺少功能或真实缺陷时，拆成独立任务，先按原契约收口结构改动。
- **第 1 步先立行为锚**：动任何结构前，必须先跑通锁定现行行为的特征测试、输出快照或等价对比脚本（没有覆盖就先补锚定测试；**仅类型检查与 Lint 绿灯不算行为锚**）。
- **第 2 步先减后加与同波次清退**：先删死代码、内联只有 1 个调用方的转发包装、拿掉冗余校验器与孤立引用；重塑接口时在同一波次迁完所有调用方（含文档、字符串引用与旧名字）并直接删除旧 API 与只护旧实现细节的死测试，绝不留双轨兼容层。
- **第 3 步等价实跑与唯一保留判据**：对照 `<repo>/docs/verify.md` 跑旧版与新版输出等价比对，严禁凭编译通过宣布完成；**以“是否切实降低读者理解负担（调用浅、隐藏可变状态少、新人 30 秒内能看清某状态从哪来、谁能改）”作为唯一保留判据——若未降低，整块回退**。

## 三、 模式 3：隔离区丢弃式原型 (`scratch/`)

- **唯一触发条件**：仅用于消除**靠跑一次实测就能拍板**的具体设计、交互手感或性能时序分叉（没有待定分叉直接走模式 1）。
- **彻底隔离与允许速成**：在仓库外或隔离 `scratch/` 目录搭建（严禁碰生产源码目录），**明文豁免正式代码规范与单元测试**，用最轻量栈快速做出来；多方案对比时放在同一个切换器（按钮或按键）里同屏实测、打日志或截图。
- **定案即弃用**：向用户展示对比证据、权衡与明确推荐；拍板后彻底作废原型，切回模式 1 按正式类型与边界规格重建生产代码，严禁把 `scratch/` 里的草稿直接合入。

---

## 四、 模式 4：像素级视觉对齐（与 `a8-ui-design` / `a8-ui-verify` 联动）

- 界面风格与布局重构先对照 [a8-ui-design](../../a8-ui-design/SKILL.md) 核对企业级秩序、极简边线、无色块孤岛与多入口同源一致性；
- 要求像素级对齐迁移时：**先建立并冻结基线截图与像素对比脚本**（缺基线严禁动组件代码），严格执行三条反作弊规则——**严禁改基线图、严禁改测试桩放水、严禁为了凑像素通过而扭曲组件结构**（认为基线有误立即停步请示）；
- 共享基础控件先迁，独立业务组件分工作区并行推进，每个组件在 [a8-ui-verify](../../a8-ui-verify/SKILL.md) 或像素对比脚本跑出 `0` 像素差异后收口。

---

## 五、 独立注释清查、实证对抗与交卷收口

1. **独立视角注释清查白名单**（写完代码后以“作者不准替自己的注释辩护”标准清查 Diff；跨文件大改或用户要求清注释时，派 1 名未参与写码的独立只读子代理扫描）：
   - **仅允许保留以下 5 类注释**：① 版权与许可证头；② 外部依赖、操作系统或协议强加的不可改怪异限制；③ 规则确有缺陷或纯样式限制的 Lint 豁免；④ 对外公开 API 文档注释；⑤ 说明代码本身表达不出来的关联 Issue 或 `docs/records/` 链接。
   - **一律删除并直接改码根治**：叙事分隔条、复述变量/函数名的翻译注释、被注释掉的死代码、`TODO/临时/别删/暂时这样` 等长篇自保说辞——遇到 `请勿删除` 先查 `git log` 核实原因，若仍成立则提议升级为类型约束、单测或 `scripts/lints/` 后再删注释；本仓自己写出的意外逻辑直接靠改名、抽类型或重定架构消除意外；**用来遮掩真实 Bug 或安全问题的 Lint 抑制注释必须连注释带隐患一起删掉根治**。
2. **高危实证对抗检查（按需触发）**：
   - 除了高架构风险触发的 `a8-judge` 与复杂跨文件触发的 `/a8-dsh-review`，对有争议的核心改动可加派 1 名只读审查者专门写命令或临时脚本去击穿设计意图，**只采纳实际跑出失败的发现，所有纯主观猜想与命名挑刺一律丢弃并标明丢弃数与原因**。
3. 执行 [SKILL.md](../SKILL.md) §4 A8 统一交卷收口（跑通 `<repo>/docs/verify.md` 命中真实表面、按门槛触发 `a8-judge` / `/a8-dsh-review`、按需写入 `docs/records/` 并利用当前上下文顺手轻更新常青与验证地图、输出 40 行以内交付简报）。
