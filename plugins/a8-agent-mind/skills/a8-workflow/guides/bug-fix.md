# 指南 2：缺陷根治闭环 (`bug-fix`)

> **适用场景**：定位并根治功能缺陷、回归故障、并发/状态错乱，或核验已有修复。  
> **硬红线**：每行修复必须有运行期实测证据支撑；“加上也许更稳”的猜测保护不得合入，被证伪的试探代码立即删净。

---

## 1. 先查是否已有修复
- 动手前先查近期 `git log`、本地分支与 `docs/records/`；
- 若已有修复补丁，切换为**核验模式**（旧基线复现故障 → 新版本证实消失且无新问题），**严禁盲目覆盖重做**。

## 2. 最轻量真实复现（不复现不写修复，不自动拉重型 UI）
- 优先使用成本最低的真实复现路径（单测、CLI 命令、最小脚本或现场日志）**稳定复现 1 次坐实根因**即可（不自动重复跑多轮重型端到端，不自动调 `/a8-ui-verify` 浏览器自动化，除非用户明确要求）；仅偶发竞态时才重跑确认稳定性。
- **严禁造假症状**：禁止往 DB/配置/内存强塞假异常数据装复现；仅本地缺失专有硬件/权限时写明卡点再请用户协助。

## 3. 二分排错、源头根治与连败 2 次熔断
1. **二分排除**：列出竞争假设，每轮选最能砍半排查空间的分界点加只读探针验证，直至唯一根因被实测坐实。
2. **源头根治**：先问“触发故障的前置状态在业务上本该存在吗？”——非法状态必须在最早构造它的上游消灭，**严禁下游判空、静默返回、吞异常，或把窄兜底（如 `ENOENT`）放宽成吞所有失败**。
3. **同前提连败 2 次强制停笔**：基于同一假设改 2 次仍卡同一失败，**严禁写第 3 次补丁**——把共同隐含前提写成一句话，先跑 1 个观测实验直接证伪该前提，再从源头重治。

## 4. 最小修复、务实 TDD 与防假测
1. **跨边界先定形状**：跨函数/模块边界先查清调用方重定签名；顺手清理同仓同源错误（$F \times S < 10$ 罕见假想边缘仅记录不改码）。
2. **仅限后端的务实 TDD（前端完全免 TDD）**：后端缺陷存在低成本本地单测路径时先写聚焦外部行为的失败测试 → 确认红灯 → 写最小修复转绿；**前端缺陷完全不走 TDD**（直接通过编译/Lint 与真实运行表面复验），后端若拉测环境沉重或需造大堆脆弱 Mock 亦明文跳过单测，直接用 `docs/verify.md` 真端到端命令作回归凭证。
3. **双反证检视测试**：故意改错业务仍绿灯 = 假测必写严；只改私有实现就变红 = 死绑实现必改测外部契约；不死卡脆弱报错全文。
4. **清净残留**：删净排查期临时日志、开关与被证伪的试探代码。

## 5. 同表面复验与交卷
- 必须回到第 2 步复现成功的**同一真实运行表面**复验（单测绿不算修完）；
- 按 `SKILL.md` §4 收口，交卷简报原样贴出“修复前失败 → 修复后通过”的真实命令输出（长日志放 `logs/`）；涉及深层根因/跨模块契约时写 `docs/records/YYYYMMDD-BUG-...md` 并顺手轻更常青与验证地图（禁起 `docs-sync`）。
