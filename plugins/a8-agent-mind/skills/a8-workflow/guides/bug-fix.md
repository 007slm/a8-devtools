# 指南 2：缺陷根治闭环 (`bug-fix`)

> **适用场景**：定位并修复功能缺陷、回归故障、并发/状态错乱，或核验已有的修复补丁。
> **核心铁律**：每一行改动代码都必须有运行期实测证据支撑。“加上也许更稳”的猜测性保护不算修复，不得合入；一旦某条假设被证据推翻，连同它带出来的试探代码一起删掉。

---

## 一、 5 步缺陷根治流程

### 第 1 步：先查是否已有现成修复
- 动手排查前，先检索近期 `git log`、本地分支与 `docs/records/`，确认目标现象是否已有合并提交或待验证补丁。
- **若已存在修复补丁**：立即切换为**“核验现有修复”模式**——在未打补丁的基线上实测复现同一故障，再到已打补丁的版本上证实故障消失且未引入新问题。**严禁在现有修复上盲目覆盖重做，也不借机顺手大改已有修复。**

### 第 2 步：真实表面独立双次复现（不复现不写修复代码）
- **查验证地图亲自动手**：先读取 `<repo>/docs/verify.md` 与目标仓库 `AGENTS.md`，找到故障所属模块的真实运行表面（涉及界面问题的配合 [a8-ui-verify](../../a8-ui-verify/SKILL.md)）；由 Agent 亲自跑出故障，**绝不把“你帮我重现一下”甩给用户**，除非客观受限于本地缺失硬件/专有权限且写明已推进到哪一步卡住。
- **独立双次复现门禁**：
  1. 写清正常预期终态与故障错误终态的分界点；
  2. 沿真实路径触发并观察到分歧症状；
  3. 清理或重置影响状态的缓存、文件或会话，**保证第二次尝试彼此独立**；
  4. 按同一路径完整再跑一遍，确认稳定出现同一故障，并用只读手段核对底层真实状态（真实文件、数据库行、HTTP/IPC 响应或日志）。
- **严禁造假症状**：检查内部状态一律只读，**绝对禁止向数据库、内存变量或配置里强塞异常数据来假装复现故障**。拿不到真实复现，严禁进入改码阶段。

### 第 3 步：二分排错、源头审视与连续失败熔断
1. **二分排除法定位**：列出竞争假设，每轮挑选最能砍掉一半排查空间的分界点，添加只读探针、日志或抓现场状态运行验证，逐个淘汰直至唯一根因被运行期证据坐实（历史回归或跨模块连带可并行按 [analyze.md](analyze.md) 查 `git log` 与爆炸半径）。
2. **区分合法状态与非法状态（源头根治铁律）**：
   - 先审问：*触发崩溃或错乱的前置状态，在业务上本应存在吗？*
   - 仅当该状态属于合法正常分支时，才在当前位置做处理或分支收敛；
   - **如果这个状态根本不该被构造出来，必须在最早产生错误状态的上游源头修复**；严禁在下游加防御判空、静默返回或吞掉错误；
   - **反例红线**：严禁把针对特定前置条件的窄兜底（如找不到某可执行文件时的 `ENOENT` 回退）放宽成吞掉所有非零失败的宽泛兜底。
3. **同前提连续失败 2 次即停手证伪前提（硬熔断）**：
   - 当基于同一条假设改了 2 次，都在同一个测试或门禁上继续失败时，**强制停笔，严禁写第 3 次补丁**；
   - 把前两次改动共同依赖的隐含前提写成一句话；
   - 设计并执行 1 个能直接反驳该前提的观测实验（重点看失败在各场景/样本上的**分布规律**，而不仅看报错大小）；
   - 一旦前提被推翻，追查所有失败样本的共同来源，从根源改变把系统推入坏状态的条件，不堆砌事后擦屁股代码。

### 第 4 步：最小根因修复、务实 TDD 与测试质量把关
1. **跨边界先定形状再写修复**：若修复跨越函数或模块所有权边界，先排查全部调用方并按最小负担重定签名与数据约束；修完顺手扫清同仓库内完全同源的同类错误模式（但**属于 $F \times S < 10$ 罕见假想边缘的，仅记录不改码**）。
2. **务实 TDD（仅在低成本路径上先红后绿，禁造假测试）**：
   - **适用条件**：目标 Bug 存在低成本本地单元测试或独立脚本验证路径（或用户明确要求补回归测试）时，先写一个聚焦外部预期行为的最小测试 → 先跑一遍确认因目标缺陷而失败 → 写最小生产修复代码 → 复跑转绿；整理提交时按“失败回归测试在前、修复提交在后”顺序放置；
   - **豁免条件**：若写单测需要拉起沉重外部环境、伪造大堆脆弱 Mock 或依赖脆弱时序，**明文跳过新建单测并写清理由**，直接使用 `<repo>/docs/verify.md` 指定的真实端到端验证命令作为回归凭证（宁可不加假单测，也不留垃圾测试）。
3. **双反证法检视测试真伪**：
   - **防假绿**：故意改错业务产出或跳过关键外部副作用时，如果测试仍绿灯 → 说明断言太松或测试自己用同一套错逻辑算预期，必须写严；
   - **防死绑实现**：保持全部外部可见行为不变、只调整私有实现时，如果测试变红 → 说明测试绑死了内部细节，必须改测外部契约或删掉；
   - 断言调用方真正依赖的错误类型或状态码，不死卡脆弱的报错字符串全文。
4. **清干净试探性残留**：彻底删掉第 3 步排查时临时加的日志、开关，以及被证伪假设留下来的试探性保护代码，确保只提交最小必要改动。

### 第 5 步：同表面复验与 A8 交卷收口
- **必须回原表面复验**：回到第 2 步复现成功的**同一真实运行表面**重跑验证，核对原缺陷消失且相邻状态、输入与错误路径未受破坏（仅单元测试通过不算修完，也不得换另一套 Mock 测试蒙混）。
- **按 [SKILL.md](../SKILL.md) §4 执行 A8 收口**：
  - 常规局部 Bug 修复免派发 `a8-judge`；若根因涉及底层机制、多阶段状态机或跨模块契约，按 [templates/work-record.md](../../../templates/work-record.md) 写 `docs/records/YYYYMMDD-BUG-...md`，并在当前上下文顺手轻量化同步 `docs/evergreen/` 与 `docs/verify.md`（勿额外调用 `docs-sync` 子代理，全量补齐交由每晚 20:00 定时梳理）；
  - 交卷简报中写清：故障现象、根因链条、最小修复与验证方式，并**原样贴出“修复前失败 → 修复后通过”的真实命令输出或日志摘录**（长日志落盘 `logs/` 贴路径）。
