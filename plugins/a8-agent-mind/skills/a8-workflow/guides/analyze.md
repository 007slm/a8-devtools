# 指南 1：只读深度分析与现场取证 (`analyze`)

> **适用场景**：解释代码机制与联动原理、追查 Git 历史动机、跨会话找回上下文、评估改动爆炸半径、活进程性能/泄漏实时取证、离线剖析文件分析、问题分诊定责。
> **不可逾越红线**：**本指南严格只读，严禁修改任何业务源码、配置文件或提交代码。** 分工说明：只读调研，不涉及多路代码写入。若排查后需要改码修 Bug 或做新功能，明确交出诊断结论后切换至 [bug-fix.md](bug-fix.md) 或 [feature.md](feature.md)。

---

## 一、 模式选择与调查动作

根据提问性质选用以下 1 种或多种调查模式（均在只读前提下推进）：

### 1. 机制梳理与渐进式图解
- **通查调用链与所有权**：可派 1 个只读探索子代理追踪相关入口、核心数据结构、状态所有权归属与非显而易见的边界条件（若需追查“为何如此设计”，同时并行走第 2 节历史溯源）。
- **结论组织格式**：
  - 说明类问题按 **概览 / 核心概念 / 运行机理 / 源码位置 (`file:line`) / 常见坑点** 组织；
  - 方案抉择类问题直接输出**对比选项利弊表**，并给出明确判断（用户前提有误时直白推翻前提，不迎合错误假设）。
- **渐进式图解规则**：讲清 3 个及以上组件联动时，禁止一上来放塞满几十条边的全量终图；用 Mermaid 先画只有 2 个核心节点的图，再分步每次只加 1 个组件或 1 条返回边，让读者看到关系是怎么一步步搭起来的；先给 1～2 句最小完整解答再按需展开，禁止打印多余的表演性总结小标题，一个概念自始至终只用一个名字。

### 2. Git 历史动机与跨会话上下文重建
- **历史动机溯源**：用 `git log -S`、`git log -L`、提交说明及仓库 `docs/records/`（注意核对顶部 `[已失效]` / `[部分失效]` 横幅）查找某个接口形状、状态守卫或硬编码阈值的来历。
  - 必须严格区分三类证据：**引用原文**（注明 Commit SHA 或记录文件名） / **`[推断]`**（基于上下文推演的可能原因） / **记录空白**（老实写明“历史记录未写明原因”，严禁编造）。
- **跨会话找回上下文**：
  - 锁定**当前目标工作区**专属的对话记录目录与时间窗（如最近 7 天），按修改时间倒序查找 `transcript.jsonl`，**严禁跨无关项目目录全局翻找历史聊天**；
  - 超过 2 份长会话日志时，派只读子代理先按主题过滤再抽取摘要，原始长日志留在子代理内不回灌主会话；
  - **以仓库现况校验历史结论**：拿到历史分支、提交或记录线索后，必须用当前 `git status`、`git log` 与 `docs/records/` 核对现况（防止把已回退或作废的设计当现状）；
  - 按四段收口返回：**5 条以内总览胶囊** → **各工作线单行状态**（标清已合入 / 进行中 / 已验证未提交 / 已回退 / 待启动） → **5 条以内反复踏空问题** → **下一步唯一具体动作**。

### 3. 改动影响面排查与 5 级确信度阶梯
评估一处小改动或未知补丁会影响多大范围时，列直接调用方只算起步，必须重点排查文本检索看不到的隐藏断链：
- **向下找穿检索盲区**：顺三层下游消费者继续查：第三方依赖本地锁死版本、数据库列类型与迁移脚本、跨端传输协议（gRPC / JNI / HTTP JSON 字段名）、原生编译配置（如 GraalVM 反射与 JNI 注册）、异步卸载与定时器生命周期、特性开关以及另一门语言读取同一批字节的路径。
- **找出“之所以安全的 1～2 个核心事实”**：别只交一份看起来头头是道的风险长清单；把整个安全判断所依赖的那 1～2 个关键事实挑出来，写一个最小验证脚本去调用真实代码证实它（若证伪则大声报错），并如实标出每个安全事实停在以下哪一级：

| 确信级别 | 实证程度 | 判定效力 |
| :---: | :--- | :--- |
| **1 级** | 仅口头推断“应该没事” | 无效，不能作为放行依据 |
| **2 级** | 指向了真实 `file:line` 或依赖源码 | 可解释路径，但未排除运行时条件 |
| **3 级** | 逐步推演证明异常情况走不到该路径 | 静态推理成立，未实机过关 |
| **4 级** | 写出并实跑独立脚本直接调用真实代码验证 | 高可信实证 |
| **5 级** | 在真实运行应用或端到端环境完整复现核对 | 最高实证 |

- **分类交付**：严格分开列出「确认存在的风险（说明触发概率、故障后果、真实 `file:line` 与复现脚本）」与「已排查并排除的风险项」。

### 4. 活进程现场取证 vs 离线剖析转表
- **活进程实时取证**（针对内存持续增长、CPU 空转、界面闪烁或锁卡死）：
  - 严禁靠读源码猜哪一行慢或泄漏。直接对运行中的目标进程采集 CPU 剖析、堆快照、线程栈、JFR 或浏览器 CDP 轨迹；
  - 大体积剖析产物交给只读子代理提取热点函数、从泄漏对象回溯到根的引用链或无输入空转循环，主会话只拿压缩后的根因片段；
  - 用低侵入只读探针或临时观测证实因果机制成立后，精准标回源码的 `file:line` 与产物路径，不顺手改业务代码。
- **离线剖析转表**（针对已有 `.cpuprofile`、`.json.gz`、堆快照或线程 Dump）：
  - 既然已有现场记录，不要直接重跑原程序掩盖旧数据；先由子代理用脚本把原始剖析档转入可查询结构（如按采样点/栈帧/节点写入 SQLite 或聚合统计表）后再分析；
  - 查出占用最高时间的栈帧路径、持有链或阻塞等待锁，**并利用产物自带符号表还原到源码 `file:line`**（缺少符号时直说产物不含符号，不算完成定因）；
  - 结论中必须明确标明：**“有改动前/后成对产物交叉证实”** 还是 **“仅靠单份产物支持的最强假设”**。

### 5. 问题分诊 5 分类与源头定责
接到异常反馈先查明完整因果再定性，禁止仅按报错表面所在的组件直接指派责任：
1. **5 分类定性**：`功能缺陷（偏离预期行为）` / `性能退化（可测量的耗时/内存/卡顿异常）` / `需求变更（当前实现符合设计但用户想要新行为）` / `使用咨询（说明用法或配置）` / `模块错分需改派`；边界不清时不乱立缺陷单，先抛出 1 个聚焦澄清问题。
2. **源头定责**：顺着触发操作一直追到真正第一次偏离预期的源码模块与近期相关提交，检查是否已有提交或未合入修复覆盖同一问题；仓库只读信息不足时老实写“线索不足以定责”，严禁猜一个责任人。

## 二、 交付输出要求

按问题类型直接交付精炼结论，必须做到：
- 每项关键判断附真实 `file:line`、Commit SHA、产物路径或实测命令输出，并标明 `[实测]` / `[推断]` / `[待确认]`；
- 如评估“是否确认安全 / 是否确定根因”，给出基于事实的直白判断与理由，不讲违心奉承话；
- 若用户要求据此改码，说明需切入的指南（[bug-fix.md](bug-fix.md) 或 [feature.md](feature.md)）后结束调查。
