# 指南 1：只读深度分析与爆炸半径 (`analyze`)

> **适用场景**：理清模块运行机理、追查 Git 历史动机、评估改动影响面（爆炸半径）、活进程现场取证。  
> **硬红线**：**严格只读，严禁修改业务源码、配置文件或提交代码。** 需要改码时先交诊断结论，再切入 `bug-fix.md` 或 `feature.md`。

---

## 1. 运行机理与渐进图解
- **通查调用链与所有权**：复杂调研可派 1 个只读探索子代理追踪入口、数据结构与状态所有权，主会话只收结构化结论与 `file:line`。
- **结论格式**：说明类按「概览 / 运行机理 / 源码位置 (`file:line`) / 常见坑点」答；方案抉择直接给利弊对比表与明确判断（前提有误直白指正）。
- **渐进图解**：讲清 3+ 组件联动时，先画 2 个核心节点，再每次加 1 块或 1 条边，避免一上来堆几十条边；同一概念只用一个词。

## 2. Git 历史动机与现况核对
- 用 `git log -S`、`git log -L` 与 `docs/records/`（核对顶部 `[已失效]` / `[部分失效]` 横幅）追查设计来历；
- 严格区分 **引用原文（附 Commit SHA / 文件名）**、**`[推断]`** 与 **记录空白（老实说没写，禁编造）**；
- 历史线索一律用当前 `git status` / `git log` 核实，防止把已回退的旧方案当现状。

## 3. 改动爆炸半径与 5 级确信度
评估改动影响面时，不止查直接调用方，必须向下找穿文本搜索盲区：
- **重点排查盲区**：依赖锁死版本、DB 列类型与迁移、跨端协议（gRPC / JNI / HTTP JSON 字段）、原生编译配置（GraalVM 反射/JNI）、异步卸载/定时器、开关与跨语言读写路径。
- **实证核心安全前提**：挑出“之所以安全”最依赖的 1～2 个关键事实，写最小脚本调用真实代码验证（证伪直接报错），并标明停在哪一级：
  - **1 级** 口头猜“应该没事”（无效）｜**2 级** 指到源码 `file:line`｜**3 级** 静态路径推演｜**4 级** 写脚本实跑真实代码｜**5 级** 真机端到端复现。
- **分类交付**：严格分开列出「确认风险（触发概率、后果、`file:line`、复现脚本）」与「已排查排除项」。

## 4. 活进程性能/泄漏现场取证
- 遇到内存增长、CPU 空转、锁卡死，**严禁靠读源码猜原因**：直接对运行进程采 CPU 剖析、堆快照、线程栈、JFR 或浏览器 CDP 轨迹，大产物留给只读子代理提炼并回标源码 `file:line`。
- 已有离线剖析档时先分析旧档再决定是否重跑，标清“改动前后成对证实”还是“单档最强假设”。
