# A8 Brain · 个人 LLM Wiki 知识大脑与头脑风暴 (`a8-brain`)

> **纯手动触发纪律**：仅在用户显式输入 `/a8-brain`（含 `定名` / `reframe`）、`A8 头脑风暴`、`头脑风暴`、`查知识库`、`整理知识库`、`知识库体检`，或由 A8 DevTools / Sidecar「知识大脑」面板一键唤起时激活；日常编码、排障与问答**严禁自动加载**，保持零日常 Token 开销。

---

## 零、定位个人知识库根目录（每次先做）

1. 本技能位于 `<plugin_dir>/skills/a8-brain/SKILL.md`，`<plugin_dir>` 即向上两级目录（通常为 `plugins/a8-agent-mind` 或 `%USERPROFILE%\.gemini\config\plugins\a8-agent-mind`）。
2. 读取 `<plugin_dir>/config.json`：
   - 若存在非空 `wiki_dir` 字段，则以该路径作为知识库根目录 `<wiki_root>`（相对路径按 `<plugin_dir>` 解析，`~` 展开为用户主目录）；
   - 否则默认 `<wiki_root> = <plugin_dir>/wiki`。
3. 知识库采用 **LLM Wiki** 五件套结构：
   - `SCHEMA.md`：整理规范、分类约定与冲突处理规则；
   - `index.md`：全库按分类组织的导航目录（每条附一句话摘要）——**查阅第一入口**；
   - `log.md`：追加式操作日志（记录每次整理 / 体检 / 回写）；
   - `raw/`：用户随时粘贴的原始素材收件箱（Twitter 帖子、文章摘录、随手记、链接）；**严禁改写或删减原始正文**，整理后只改 Frontmatter 的 `status` 与 `ingested_at`；
   - `pages/`：由 Antigravity 维护的互链知识页（使用 `[[slug]]` 或 `[[slug|显示名]]` 互链）。

## 一、模式路由（按用户意图择一执行）

| 用户意图 | 模式 | 一句话目标 |
| :--- | :--- | :--- |
| 提出具体问题、讨论方案、要求头脑风暴或查知识库辅助分析 | **Mode 1：头脑风暴（默认）** | 先读 `index.md` 挑 2～5 篇最相关条目精读，用库中原则/模式/玩法拆解问题并显式引用 `[[slug]]` |
| 要求整理素材、归档随手记，或面板点击「回 Antigravity 整理」 | **Mode 2：整理归档（Ingest）** | 消化 `raw/` 待整理素材 → 写入/合并 `pages/` 并建双链 → 更新 `index.md`、`log.md` 与 `raw/` 状态 |
| 要求体检知识库、排查断链/孤立页/重复冲突 | **Mode 3：知识库体检（Lint）** | 扫出断链、孤立页、漏登索引、重复/冲突条目，给报告并按确认修复 |

## 二、Mode 1：头脑风暴与辅助分析（Query & Brainstorm）

1. **极省 Token 渐进阅读**：
   - 先只读取 `<wiki_root>/index.md`（切忌一次性读取所有 `pages/` 文件）。
   - 根据当前话题，从 `index.md` 中精选 **2～5 篇**最相关的 `pages/*.md` 精读；若命中线索指向某篇未整理的 `raw/` 笔记，再按需补读该 `raw/` 文件。
   - 若知识库尚为空或未命中相关条目，如实告知用户“当前知识库暂无直接相关条目”，仍按第一性原理展开头脑风暴，并在末尾提示可沉淀的切入点。
2. **批判性镜子人设与结构化输出**（客观理性、反迎合、批必带建、深挖 Why 而非止于 What）：
   - **① 审视前提与直指盲区**：先审视用户原始提问或设想中的隐含假设、盲区、低估风险与机会成本；若原问题问偏或推理薄弱，直接剖析底层原因（Why）并重构为更犀利的问题（前提无硬伤则不硬挑刺，严禁为了反对而反对）；
   - **② 调取的知识武器**：用 `[[slug]]` 列出本次引用的条目，并各用一句话点明借用了其中的什么原则、方法论或反模式；
   - **③ 多视角拆解与方案碰撞**：结合知识库框架与重构后的问题，给出 **2～3 条有实质差异的思路/方案**（含用户尚未考虑过的视角，每条讲清适用前提、核心动作与代价/风险）；
   - **④ 优先级落点与下一步**：按优先级给出精准可执行的最小验证动作，不强行替用户改代码或写文件。
3. **知识复利闭环（仅询问，不擅自改库）**：
   - 若本次讨论产生了值得长期复用的新方法论、模式或对比结论，在回复末尾用一句话询问：“是否要把本次核心结论沉淀为新 Wiki 条目 `pages/<suggested-slug>.md`？”仅在用户确认后落盘。

## 三、Mode 2：整理归档（Ingest）

1. **读取上下文**：
   - 读取 `<wiki_root>/SCHEMA.md`、`<wiki_root>/index.md`，以及用户指定的 `raw/*.md`（若未指定具体文件，则检查 `raw/` 下所有 `status: pending` 的文件）。
2. **消化提炼与网络融合（拒绝简单搬运原文）**：
   - 从原始素材中提炼**可跨项目复用的核心观点、操作原则、多 Agent / Skill 模式、反模式与适用边界**；
   - 对比 `index.md` 判断每个知识点应：
     - **合并更新**已有 `pages/<slug>.md`（保留已有精华；若新旧观点有分歧，显式写明「观点演进 / 适用条件分歧」，严禁静默覆盖历史洞见）；或
     - **新建** `pages/<slug>.md`（文件名使用简洁 kebab-case 英文或语义 slug，如 `subagent-context-isolation.md`）。
   - 规范写入 `pages/<slug>.md` 的 YAML Frontmatter：
     ```yaml
     ---
     title: "条目中文标题"
     category: "Agent 与 Skill 玩法"
     tags: ["subagent", "workflow"]
     summary: "一句话提炼核心洞见，用于 index.md 快速定位"
     sources: ["raw/20261122-xxx.md"]
     updated_at: "YYYY-MM-DD HH:MM"
     ---
     ```
   - **双向互链**：在新/改页面正文用 `[[slug]]` 或 `[[slug|可读名]]` 链接相关条目；同时检查被关联的旧页面，按需补上一处自然的交叉引用链接，形成真正的知识网络。
3. **同步收口三件套**：
   - 更新 `<wiki_root>/index.md`：按 `category` 分组插入或更新条目（格式：`- [[slug|条目标题]] — 一句话摘要`），确保所有 `pages/` 页面都有索引；
   - 向 `<wiki_root>/log.md` 追加一条带时间戳的整理记录（列出本次处理的 `raw/`、新建/更新的 `pages/` 与新增关联）；
   - 将已处理完的 `raw/*.md` 的 Frontmatter 中 `status` 改为 `ingested`、`ingested_at` 填当前时间（**保持 `---` 之后的原始正文原封不动**）。
4. **简洁汇报**：汇报本次处理的原始素材数、新建/更新的 Wiki 页面、建立的关键链接以及遗留待确认问题（若有）。

## 四、Mode 3：知识库体检（Lint）

1. 扫描 `<wiki_root>/index.md`、`<wiki_root>/pages/**/*.md` 与 `<wiki_root>/raw/*.md`，检查 5 类健康问题：
   - **断链**：正文中的 `[[target]]` 指向不存在的条目；
   - **孤立页**：既没有出链也没有任何入链（Backlinks）的 `pages/` 页面；
   - **漏登索引**：存在于 `pages/` 但未出现在 `index.md` 中的页面，或 `index.md` 指向已删除文件的死入口；
   - **重复与冲突**：主题高度重叠可合并的页面，或存在未标注权衡条件的矛盾结论；
   - **待整理积压**：长期停留在 `status: pending` 的 `raw/` 素材。
2. 对纯机械修复（补齐 `index.md` 漏项、修明显拼写断链）可直接给出清单并在用户确认后修复；对概念合并或删改，先列建议由用户拍板。

## 五、Mode 4：概念定名与问题重构（Reframe）

适用于“能说出症状或粗略想法，但喊不出准确行业概念，导致无法精准指挥 AI 或选错架构方向”的场景。**本模式严禁修改业务源码。**

1. **真实材料与知识库双起步**：
   - 若涉及当前仓库的具体代码、报错、日志或设计文档，先直接读原始文件与用户原话（不看二手概括）；
   - 顺手扫一眼 `<wiki_root>/index.md`，若知识库已有相关模式或概念，优先复用并标注 `[[slug]]`。
2. **模糊问题消歧（多义先拆）**：
   - 若原始描述可能指向 2～3 类本质不同的问题，先列出每种候选问题的**标准定名**与**一眼区分的判别信号**，明确锁定最可能的一类并说明判断理由；问题定性本身已清晰则直奔下一步。
3. **精炼核心专业术语（3～6 个，按对架构/实现的影响力排序）**：
   - 严禁为凑数堆砌黑话，只给真正会改变实现方案的关键概念；
   - 每条写清 4 项：**标准术语（英文原词 + 一句大白话）**、**对应当前描述或代码的哪部分**、**已知经典项目/论文/系统参考**（取消强制逐条抓外链，确有实据或必要核查时再附实测链接，**严禁编造未核实的 URL**），以及**学会这个词后能直接向 AI 要什么**。
4. **跨领域类比与断裂点（1～2 个相邻领域）**：
   - 挑 1～2 个解决过“同形问题”但叫法不同的相邻领域，说明**哪些思路和词汇可迁移回来**，并明确指出**类比在哪里失效**（防生搬硬套）。
5. **盲区提醒、精准重写与复利收口**：
   - 点出用户没提到但必须关心的 1～3 个关键边界/隐患；
   - 在 Markdown 代码块中输出一段**「术语重构版描述」**，并提示用户可直接开工，或转发给 [`/a8-prompt`](../a8-prompt/SKILL.md) 结合目标仓 `AGENTS.md` / `docs/verify.md` 深化为可执行任务书；
   - **知识复利闭环**：若本次提炼的领域词表或跨领域心智模型值得长期留存，末尾用一句话询问是否沉淀为 `pages/<suggested-slug>.md`（仅在用户确认后落盘）。
