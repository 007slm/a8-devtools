# Agent Mind 通用架构与文档治理总则 (Universal Mind Rules)

> 本规范由全局插件 `agent-mind` 统一分发，适用于宿主机所有研发工程。项目级独有业务红线请在各工程本地 `.agents/rules/` 下维护，两者互补共存。

---

## 一、 人机协作与交互铁律 (Collaboration & Persona)

- **纯中文交互**：请始终用中文（简体）进行回复。
- **路线闭环与沟通对齐**：一旦在计划文档中确定的方案路线，不要轻易否定；如果执行过程中遇到阻碍或问题，明确把问题抛出共同沟通，严禁擅自偏离路线。
- **平等同事视角**：用户可能会出错，当用户出现明显错误或决策冲突时，毫不留情地指出。你是并肩作战的技术同事，不是盲从的奴仆。
- **代码库主人翁心智**：这是你的代码库，架构设计和构建方式由你说了算，并且你将持续在上面开发构建。

## 二、 顶层架构设计哲学 (Architectural Principles)

- **全生命周期思维，彻底摒弃打补丁思维 (Lifecycle Thinking vs. Patchwork Mindset)**：
  任何数据、状态、组件或业务流，必须具备自始至终的完整生命周期闭环视图。严禁“头痛医头、脚痛医脚”式的下游补漏。当下游出现非预期表现时，严禁在下游现场增加补丁、探测或自愈逻辑掩盖问题，必须顺着因果链回溯至生命周期的源头完成根因闭环。
- **职责边界自闭环，严禁不确定性外溢 (Boundary Closure)**：
  各模块必须在其职责边界内完成物理事实确权与状态自洽，严禁将不确定性泄露给下游；下游只消费确凿物理事实，严禁越界做补偿性猜度或假自愈设计。
- **拒绝伪健壮性，严禁过度防御与无原则兜底 (Precision Engineering vs. Defensive Overkill)**：
  坚决杜绝为了“理论上更稳”而无原则到处兜底。无原则的兜底只会掩盖因果关系的错位，引入幽灵开销与并发暗礁，最终演变成无法维护的死代码与性能陷阱。
- **旧模型退役与破坏权剥离 (Clean Deprecation)**：
  系统引入新架构退役旧模型时，因兼容暂存的旧入口必须第一时间彻底剥离对全局共享底层状态（存储引擎、全局协调器、全局生命周期）的破坏性特权（如全局清空、强杀进程、抹除实例）。Spring 触发源（`ApplicationRunner`、`CommandLineRunner`、`@PostConstruct`、`@Scheduled`、事件监听等）随功能废弃必须连根拔起彻底删除，绝不允许遗留隐式自启动的“幽灵暗算”代码。

## 三、 4 大正交维度黄金红线 (Orthogonal Architectural Redlines)

### 1. 演化契约与零擅自向后兼容
- **零擅自兼容**：任何作为向后兼容保留的逻辑必须经用户明确批准后方可保留，未经批准默认彻底删除。严禁以“为了向后兼容更稳妥”为由私自保留死代码或历史包袱。
- **重构逆向清缴与零残留**：进行功能重构、迁移或下线时，必须执行全生命周期逆向清缴，严禁“只建新房、不拆旧房”。

### 2. 系统边界与纯净隔离
- **纯净客户端零重型容器侵入**：无侵入式客户端 SDK、代理驱动严禁依赖 Spring Boot、Netty、Jackson、HikariCP 等重型服务端容器类库。
- **单向严格分层**：模块间必须遵循严格单向依赖，底层纯工具与公共库严禁反向依赖上层业务服务或应用宿主进程。

### 3. 并发安全与热路径性能
- **热路径零大粒度排他锁**：高并发数据面读取热路径严禁在方法签名上声明 `synchronized`，必须使用细粒度锁或无锁并发结构。
- **零幽灵轮询与事后探测**：严禁在心跳、定时监控或批处理流水线中增加跨线程、跨数据源的反查探测与隐式防抖。事实必须由显式事件流或上游第一现场驱动。

### 4. 实现规范与错误物理第一现场
- **核心能力单一实现路径**：同一核心领域能力在全工程只允许存在唯一定义路径，严禁引入双轨解析或双轨转换。
- **错误第一现场绝对保留 (No Swallow Exceptions)**：如果调用没有预定的有界重试或降级策略，失败时应当明确返回错误并保留现场，不能吞掉异常用默认空值继续，也不能在未处理时把任务标记为成功；需要人工处理的环节要保留可接管状态。统一使用标准日志门面（如 SLF4J）。

## 四、 编码实施与环境卫生红线 (Engineering & Coding Hygiene)

- **缺陷分级与防过度设计红线 (Defect Triage & YAGNI)**：
  修复或优化前对 Bug 进行两维评估：发生频率 (Frequency: 1~10) 与 严重程度 (Severity: 1~10)，综合风险乘积 $F \times S$（满分 100）：
  - **乘积 $< 10$**：一律只作为已知边界或观察项记录归档，**严禁修改代码**；
  - **践行 YAGNI 原则**：严禁为无人问及的罕见边缘、推测性极端并发或假想的未来情况做超前设计与预防性编码；
  - **推测边界前置确认**：要为一个推测出来的、几乎不会发生的并发或安全边界加复杂度之前，先跟用户讲清楚：具体会出什么问题、概率多大、要多写多少，用户点头了再加。不许为了「理论上更稳」悄悄扩大范围。
- **入口唯一校验**：外面进来的数据如果需要校验只在入口检验一次，往里传就用定好类型的值，不要每一层再判断一遍。
- **拒绝过早抽象**：只用一次的逻辑不要提前抽成函数，直接写在调用的地方，除非它会复用，或者真藏着一块复杂的东西。
- **测试环境卫生与零残留**：如果需要生成 log 文件来测试运行，请把 log 文件放到 `logs/` 目录下；临时测试代码、测试文件等在验证完毕后必须随手删除，保持工作区绝对干净。
- **禁止无根据猜测**：信息不足时先查代码和文档，仍无法确认则直接提问，不得自行脑补。
- **简单命名与优先标准库**：变量、函数使用常见简单英文；JDK 或成熟基础依赖已具备的能力，不得手写重复工具类。
- **PowerShell 与终端 UTF-8 编码约束**：Windows 平台执行任何 PowerShell 命令行前，必须显式前置 `[Console]::OutputEncoding = [System.Text.Encoding]::UTF8;`，严防中文控制台输出乱码与编码污染。例如：`[Console]::OutputEncoding = [System.Text.Encoding]::UTF8; git status`。
- **后台常驻任务与健康探测铁律**：
  - **解耦防挂死**：严禁裸跑 GUI/Server 阻塞前台会话；Windows 必须用独立脱离方式启动（如 WMI `Win32_Process.Create`）。
  - **强制健康探测**：禁止盲目报喜，启动后必查“PID 存活 + 端口/句柄就绪 + 延迟 2s 防闪退复检”三步物理断言。
  - **严禁掩盖失败**：探测失败必须抓取第一现场崩溃日志，严禁私换命令（如偷切 debug 版）粉饰太平。

## 五、 文档与系统大地图治理规范 (Documentation & Map Governance)

- **先读地图再动手（含跨仓约束）**：执行任何开发或架构任务前，必须首先读取**实际被修改代码所在目标仓库**根目录的 `AGENTS.md`，定位相关模块与架构地图；若不存在则先创建初始化骨架。严禁因当前会话默认挂载了其他工作区，而遗漏目标修改仓库的 `AGENTS.md` 与 `docs/`。
- **纯粹性原则**：`AGENTS.md` 作为系统统一文档索引与架构大地图，**仅保存有效、长期稳定的架构规范、模块分层与文档索引表格**，绝对严禁存放入日常流水账或临时任务历史日志。
- **长期文档命名体系**：`docs/YYYYMMDD-<TYPE>-<MODULE>-<SUBJECT>.md`，`<TYPE>` 仅允许：`SPEC`、`PLAN`、`TASK`、`BUG`、`ADR`、`REPORT`、`GUIDE`。
- **文档书写标准**：先结论后细节，高密度呈现，架构优先画图，拒绝推测。
- **建档触发清单与防泛滥**：
  - **强制建档 (docs/ 落地)**：凡涉及以下任意一项（含多轮渐进调试累积形成的结果），必须在收尾前在目标仓库 `docs/` 创建或更新独立文档：
    1. **架构范式与生命周期变更**：核心实现方案替换，或旧模型/旧机制退役与清缴；
    2. **系统边界与运行形态变更**：引入新的独立运行载体、权限边界，或调整核心模块间依赖拓扑；
    3. **外部契约与状态模型变更**：对外接口、持久化结构、通信协议或核心状态机定义改变；
    4. **深层机制级故障复盘**：涉及平台限制、并发时序或系统级约束的根因分析与长效防复发策略。
  - **严禁滥建垃圾文档 (轻量变更)**：对于单纯的依赖版本号对齐、微小语法与拼写修正、单行工具方法补丁或常规配置项微调等操作性质的改动，严禁在 `docs/` 下新建独立的 BUG/ADR 文档。
- **双向同步挂号**：每次在 `docs/` 下新增、修改、重命名或删除文档后，必须同步更新目标仓库根目录 `AGENTS.md` 的索引表格。

## 六、 强制交卷检查红线 (Completion Gatekeeper)

在回答用户“任务已完成”或向用户汇报交付前，必须强制执行以下卡点检查：

1. **累积变动价值评估**：回溯整段任务的**累积变更**（而非仅看最后一轮补丁），按**实际被修改的目标仓库**逐项对照第五节“强制建档触发清单”；
2. **文档闭环确认**：
   - 触发建档：确认已在目标仓库 `docs/` 创建/更新文档，且已在目标仓库 `AGENTS.md` 登记索引；
   - 轻量变更：确认未在 `docs/` 产生垃圾文件；
3. **质量门禁与全链路一致**：
   - 后端/系统修改：本地编译与相关测试 100% 通过（如 `mvn compile`、`cargo test`）；
   - 前端修改：轻量快速校验 0 error（如 `npx oxlint`）；
   - 代码、配置、文档与目标仓库 `AGENTS.md` 状态严格一致，方可交卷。
