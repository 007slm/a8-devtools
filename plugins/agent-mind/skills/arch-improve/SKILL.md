# Experience & Taste Improvement (`arch-improve`)

本技能**只做一件事：由用户主动触发，将会话中的真实纠偏转化为下一位新 Agent 可直接执行的硬规则或机器检查**。

> **职责边界说明**：仓库 `docs/` 长期文档、仓库大地图 (`AGENTS.md`) 与全局仓库地图 (`agent-mind/repos.md`) 属于日常开发会话交卷时自动同步生成的本职工作（由 `mind-rules.md` 自动驱动），不在本技能中重复处理。

---

## 5 条核心执行铁律 (Hard Rules)

1. **只源于用户的真实意志（Only the User's Taste/Intent）**：
   - 每一条候选规则必须可追溯到用户的显式纠偏、静默改码（`Silent edit`）或明确拍板；
   - **严禁** AI 因为自己觉得“理论上算好实践”而私自往规则库添加套话。

2. **严禁编造 Why（Never Invent a Why）**：
   - 若用户在纠偏时给出了原因，原样采用用户的真实表述；
   - 若用户未给原因（仅否决、回退或手动改了代码），AI 推演出来的理由必须显式标注 **`*inferred*:`**，并列入 **`❓ 待你拍板 (Needs your answer)`** 经用户确认或改写后方可落盘——一条猜错的 Why 比没有 Why 更危险，因为下一个 Agent 会拿着错误理由错误泛化。

3. **旧规失效则收紧重写，拒绝枚举堆砌（Rewrite Stricter & Merge into Principles）**：
   - 当已有规则覆盖该问题但本次依然犯错时，说明旧规则表述太软或缺少判据，必须直接**收紧重写旧规则**；
   - 绝不按具体文件或具体组件类别逐类枚举堆砌规则，优先从**第一性原理**向上归并至已有底层工程习惯，保持规则库长期精干收敛。

4. **机器检查胜过文字句（A Check Beats a Sentence）**：
   - 机器检查每次都会执行；长文档里的一句话在上下文快满时必然被模型漏掉；
   - 凡可通过代码匹配、Lint、`judge_router.py`、Google Decisions API 准则或单测自动拦截的违规，优先提案为 **`🔍 升级为机器检查 (Make it a check)`**，规则文档仅留 1 行指针记录 Why。

5. **第一性原理 + 物理判据锚点 + 主会话提案后停步（Propose Then Stop）**：
   - 严禁“尽量/适当/如前所述”等空泛词，采用**“第一性原理主干（通用因果律与工程习惯） + 括号内 1 个具体物理判据/典型反例”**并通过零上下文独立复现自测；
   - **绝对在主会话中运行（No Subagent）**，输出 Generative UI 卡片与结构化清单后立即停步，支持 `写入全部` 或按编号精确批准（`写入 1, 3`），**严禁未经用户批准静默落盘**。

## 触发变体契约 (Invocation Variants)

| 触发指令 | 行为模式 |
| :--- | :--- |
| `/improve`、`/复盘`、`/提升` | 扫描当前会话，提炼第一性原理规则/检查项复盘报告与 Generative UI 卡片，停步等待用户确认 |
| `/improve <sessions>` | 除当前会话外，额外读取用户指定的或最近 N 个会话的 `transcript.jsonl`（`<appDataDir>/brain/<cid>/.system_generated/logs/transcript.jsonl`），捕捉跨多次会话反复出现的系统性顽疾。<br>**上下文预算红线**：严禁无差别全文读入数 MB 的 `transcript.jsonl`，必须按行流式过滤，每个历史会话仅提取最近 200 行内与 `USER_INPUT`、用户纠偏/回滚或关键决策相关的 `PLANNER_RESPONSE` 摘要 |
| `/improve prune` | 扫描目标仓库 `.agents/rules/redline.md`（及 `AGENTS.md` 关键设计决策索引）与全局 `mind-rules.md`，将零散的场景枚举条款向上归并提炼为第一性原理，消解前后矛盾，收紧包含“尽量/注意/适当/优先”的软弱规则，确认后落盘 |
| `写入` / `写入全部` / `写入 1, 3` | 仅将用户批准的编号项（以及已回答了 `*inferred*` Why、归并/层级问题项）写入对应规则文件或检查脚本 |

## 五阶段执行流水线 (Execution Pipeline)

### Phase 1：从首轮起扫描五维纠偏信号（Collect Corrections）

从第 1 轮对话一路扫描至本轮（若为 `/improve <sessions>` 则同步读取对应历史 `transcript.jsonl`）。显式批评只是少数，必须覆盖全部 5 类信号；跳过一次性业务文案调整、普通单次 Bug 修复及单纯的任务需求澄清：

| 信号类型 | 识别线索 / 示例 | 提取要点 |
| :--- | :--- | :--- |
| **1. Explicit correction（显式纠偏）** | 用户直接否定方案、指正架构误判或明确立规矩 | 记录原话规则，通常附带现成的 Why |
| **2. Silent edit（用户静默修改）** | Agent 写完文件后，用户自己手动改了配置/参数/源码（通过系统外部修改通知，或与 Agent 上次写入版本 diff 识别） | **关键盲区补齐**：Agent 默认值错了，用户的最终修改值就是真实规则 |
| **3. Repeated nudge（连续微调）** | “再紧凑点” → “还是太宽” → “行了” | 只记录**最终收敛落点**（如具体数值/阈值/边界），不记录中间试探过程 |
| **4. Revert / Rejection（回退或否决）** | “撤回”、“选 B 不选 A”、删掉 Agent 刚加的功能或防御代码 | 明确的反面红线；往往缺少原因，需标记 `*inferred*` 并进入 `Needs your answer` |
| **5. Confirmed non-obvious choice（确认非显而易见决策）** | “对，图标旁路/状态设计就这么干” | **仅当一个零背景新 Agent 极可能做出相反选择时才记录**；显而易见共识不记 |

> 每捕获一条信号，必须同时锁定：用户原话引用（或物理 Diff）、Agent 原先的错误做法、用户期望的做法、以及用户是否给出了原因。

---

### Phase 2：防膨胀过滤漏斗（Filter Tree）

对 Phase 1 捕获的每一条纠偏信号，严格按下方决策树逐层裁决：

```text
这背后反映的是可跨场景迁移的通用工程偏好/架构因果律吗？
├── 否（仅针对当前页面文案、单次一次性任务逻辑或孤立的特定文件特例）
│   └──► 归入 Skipped（单行说明跳过原因，把推翻权留给用户）
└── 是
    ├── 现有 AGENTS.md / .agents/rules/redline.md / mind-rules.md 是否已有相关规则/第一性原理覆盖？
    │   ├── 是，且方向一致（说明既有原理缺少判据锚点或表述太软导致失效！）
    │   │   └──► Rewrite Stricter / 归并收紧（在既有第一性原理上补齐半句物理判据或数值/API边界，严禁新增平行规则！）
    │   ├── 是，且互相矛盾
    │   │   └──► 归入 Conflicts（并列展示现行旧规与本次新纠偏，交用户二选一）
    │   └── 否 ──► 继续
    ├── 该违规能否通过静态匹配 / Lint / judge_router.py / Decisions API / 单测自动检测？
    │   └── 是 ──► 归入 Make it a check（提供具体可落地的检查实现 + 在规则文件留 1 行指针记录 Why）
    └── 作用域与落盘物理路径判定：
        ├── 仅限当前仓库专属架构红线 ──► 写入当前仓库 .agents/rules/redline.md（严禁把原始规则条目塞入 AGENTS.md 破坏仓库大地图纯粹性；AGENTS.md 仅在关键设计决策章节保留索引链接）
        ├── 跨场景通用工程偏好与架构习惯 ──► 优先归并/写入真源 E:\a8-devtools\plugins\agent-mind\rules\mind-rules.md（由 bindflt 实时映射全局生效）
        └── 归属或归并方式模糊 ──► 放入 Needs your answer 附推荐答案请求用户拍板
```

### Phase 3：第一性原理归因与防膨胀定尺（First-Principle Generalization）

对通过 Phase 2 漏斗、拟沉淀进规则文档的每一条纠偏，禁止直接写成“针对某个具体模块/组件类别的枚举规矩”，必须完成以下三步：

1. **第一性原理归因（First-Principle Abstraction）**：
   - **拒绝按具体文件或具体组件类别堆砌枚举**：对每次纠偏连续向上追问“背后的本质是什么”，抽取出**跨场景、跨模块可迁移的通用工程偏好或因果律（第一性原理）**；
   - **优先归并既有原理（防规则膨胀核心机制）**：先对照全局 `mind-rules.md` 与仓库 `redline.md` 既有第一性原理——若已被某条既有原理涵盖（如“边界自闭环”、“零黑窗/原生 API 优先”、“全生命周期清理”），**必须直接融入并收紧该既有条目**（补齐半句物理判据锚点），**严禁另立平行新条目**；唯有发现全新的底层通用习惯/工程价值观时，才允许新增独立条目；
   - **结构定式（原理主干 + 物理判据锚点）**：既要跨领域普适，又要防止空泛口号被新 Agent“自我合理化”绕过，固定采用**“第一性原理主干（含`必须`/`严禁`） + （括号内 1 个具体物理判据或典型反例）”**的写法（同时保留适用前提，严禁丢失前提的无差别一刀切）。

2. **自我反测门（Self-Test Before Proposing）**：
   - 在把规则草案展示给用户前，**只读“第一性原理 + 物理判据锚点”与其 Why（完全屏蔽本轮对话回忆）**；
   - 反问自己：*“一个毫无背景的新 Agent 仅凭这句话去做原先那个任务，还会因为理解过于空泛而重犯原错吗？”*
   - 如果答案是“仍然有可能”，说明括号内的物理判据锚点不够锋利（缺少清晰边界特征或反例），必须收紧锚点后再提案。

3. **标准落盘条目格式（含原话时间戳考古注释）**：
   ```markdown
   - **[第一性原理标题]**：[跨场景通用工程偏好与因果律主干，使用“必须/严禁”，禁用“尽量/适当/优先”；保留清晰适用前提（物理判据锚点：例如具体机制边界/API约束或典型反例）]。
     - **原因 (Why)**：[用户原话原因，或经用户确认后的原因]。
     <!-- YYYY-MM-DD: "用户原话摘录或 Silent edit 物理变动摘要" -->
   ```
   *(保留 HTML 注释中的日期与原话锚点，便于日后出现新旧意图冲突或执行 `/improve prune` 时快速溯源。)*

### Phase 4：嵌入紧凑型 Generative UI 卡片 + 结构化确认清单（Report & Stop）

1. **生成并嵌入 Generative UI 卡片**：
   参考 [templates/retro_card.html](templates/retro_card.html)，在 `<Artifact Directory Path>/retro_card.html` 写入本次复盘卡片并嵌入对话：
   ```html
   <agent-embed src="file:///<artifact_path>/retro_card.html"></agent-embed>
   ```
   **Generative UI 设计约束**：
   - 引入官方 Tailwind 脚本：`<script src="https://www.gstatic.com/antigravity/web/dev/tailwindcss.min.js"></script>`；
   - `<body class="bg-transparent text-[var(--foreground)] antialiased p-3">`；
   - 全部使用宿主语义颜色变量（`bg-[var(--card)]`, `text-[var(--foreground)]`, `border-[var(--border)]`, `text-[var(--muted-foreground)]`），严禁硬编码固定深浅色；
   - 卡片保持紧凑（高度尽量收敛在 **280px ~ 360px** 区间），顶部显示模式与任务主题，中部双栏呈现“五维纠偏信号捕获”与“规则动作与目标文件”，底部展示标准 `git diff` 规则/检查补丁预览。

2. **输出结构化确认清单（卡片下方）**：
   按以下 5 个固定小节呈现（**内容为空的小节直接省略**；若整场会话没有任何经验/品味纠偏，直接一行说明 `本轮会话无新增规则纠偏（零膨胀状态良好）`——“无事可学”也是优秀结果，严禁为了交差硬凑规则）：

   - **`📏 候选规则与既有原理收紧 (Rules to Merge / Rewrite / Add)`**：

     | # | 触发信号 / 原话 | 动作 | 规则正文 (第一性原理 + 物理判据锚点) | Why | 目标文件 |
     | :--- | :--- | :--- | :--- | :--- | :--- |
     | 1 | `"..."` 或 `Silent edit: ...` | 归并既有原理 / 收紧重写 / 新增原理 | `[第一性原理主干（物理判据/典型反例）]` | `[用户原因]` 或 `*inferred*: ...` | `mind-rules.md` / `.agents/rules/redline.md` |

   - **`❓ 待你拍板 (Needs your answer)`**：汇总每条 `*inferred*:` 原因、归并至某既有原理还是单列新原理、以及仓库级/全局归属问题，每条 1 行并附 AI 推荐选项。
   - **`⚔️ 规则冲突 (Conflicts)`**：并列展示现行旧规、本次新纠偏，以及保留建议。
   - **`🔍 升级为机器检查 (Make it a check)`**：给出可落地的检查代码/脚本/Lint/测试片段，以及在当前代码库中预扫描会命中的存量数量。
   - **`⏭️ 已跳过项 (Skipped)`**：每条 1 行写明被过滤的纠偏及跳过原因（如“一次性页面调整”），方便用户随时纠正“不对，这条要记”。

   结尾固定提示：
   > *请回复 `写入全部` 或 `写入 1, 3`（可同时回答上方待拍板问题）以完成落盘。*

### Phase 5：按批准项精准落盘（Write on Approval）

1. 仅写入用户在回复中明确批准的编号项（`写入全部` 或 `写入 1, 3`）以及已完成 `*inferred*` Why 确认的条目；
2. 写入规则文件后呈现 Diff 与变更摘要；
3. 对于已批准落地的 **`Make it a check`** 检查项：
   - 先落盘检查规则/脚本/测试，并在代码库实际运行一次验证；
   - 若检查命中了代码库中既有存量违规，**如实汇报命中数量与位置，询问用户是“先设为 Warn 告警”还是“立即修复存量违规”——未经允许严禁擅自借机修改业务源码。**
